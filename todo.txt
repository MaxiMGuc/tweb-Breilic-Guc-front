Ниже — постановка задач: для каждого интерактива указано, какую логику нужно
реализовать. Сами таски НЕ выполняются в рамках этого списка — только фиксация.

Пояснение: учтены элементы <button>, раскрывающиеся <summary> в шапке и
боковом меню, а также ссылки NavLink/Link, где требуется не только переход,
но и передача состояния, валидация или вызов API.

Уровни сложности (по возрастанию):
  У1 — простая логика, мало состояний, без внешних интеграций.
  У2 — средняя: несколько состояний, формы, контекст, связка экранов.
  У3 — высокая: платежи, безопасность, админ-CRUD с сущностями, интеграции API.

Метки «React» / «Бэкенд+БД»:
  [React] — таск можно полностью закрыть на клиенте (UI, валидация, mock, localStorage,
            контекст, статические данные). Подходит для этапа без сервера.
  [Бэкенд+БД] — для целевого поведения продукта нужен API и хранение (авторизация,
                 брони, оплата, персистентность профиля, тикеты поддержки и т.д.).
  У части задач сначала делают прототип [React], затем дорабатывают [Бэкенд+БД]
  (в таблице указано оба варианта там, где это важно).

ПЛАН РЕАЛИЗАЦИИ ПРОЕКТА УРОВНЯ AVIASALES (React + TypeScript + C#)

0. ВАЖНО ДО СТАРТА
0.1. Юридические и продуктовые рамки
0.1.1. Делать "аналог по функционалу", а не буквальную копию бренда, текстов, иллюстраций и уникальных ассетов.
0.1.2. Использовать собственное название, логотип, цветовую схему, иконки, тексты и дизайн-токены.
0.1.3. Проверить условия использования внешних API авиабилетов (rate limits, лицензии, атрибуция).
0.1.4. Добавить в продукт политику приватности, оферту, cookie policy.
0.1.5. Сразу заложить поддержку GDPR/локального законодательства (удаление данных, экспорт данных пользователя).

1. ЦЕЛЬ ПРОЕКТА И ФУНКЦИОНАЛЬНЫЙ ОБЪЕМ (MVP -> V1 -> V2)
1.1. Главная цель
1.1.1. Поиск и сравнение авиабилетов с фильтрами, сортировками, сохранением предпочтений, ценовыми уведомлениями.
1.1.2. Быстрый, надежный и адаптивный интерфейс (mobile-first).

1.2. MVP (первые 2-3 месяца)
1.2.1. Поиск билетов (туда/туда-обратно/сложный маршрут можно отложить на V1).
1.2.2. Список результатов, сортировки, базовые фильтры.
1.2.3. Карточка рейса с переходом к партнеру/поставщику.
1.2.4. Авторизация (email+password или OAuth), профиль с избранным.
1.2.5. История поисков и сохраненные фильтры.
1.2.6. Админ-панель для базовой аналитики и управления справочниками.

1.3. V1
1.3.1. Подписка на изменение цены (price alerts).
1.3.2. Календарь низких цен.
1.3.3. Мультивалюта и мультиязычность.
1.3.4. Гибкая система ранжирования выдачи.

1.4. V2
1.4.1. Сложные маршруты (multi-city).
1.4.2. Рекомендательный движок (персональные предложения).
1.4.3. Машинное прогнозирование цен.
1.4.4. A/B тестирование интерфейса и алгоритмов.

2. АРХИТЕКТУРА СИСТЕМЫ
2.1. Общая схема
2.1.1. Frontend: React + TypeScript + Vite/Next.js (рекомендуется Next.js для SEO страниц контента).
2.1.2. Backend: ASP.NET Core Web API.
2.1.3. БД: PostgreSQL (основная), Redis (кэш/сессии/rate limiting), Elasticsearch/OpenSearch (опционально для сложного поиска).
2.1.4. Очереди: RabbitMQ/Kafka (фоновые задачи: обновление цен, уведомления).
2.1.5. Объектное хранилище: S3-совместимое (баннеры, медиа, экспорт отчетов).

2.2. Модули backend
2.2.1. Identity Service (пользователи, роли, JWT/refresh).
2.2.2. Search Service (агрегация результатов от поставщиков).
2.2.3. Pricing/Rules Service (нормализация валют, комиссии, финальная цена).
2.2.4. Notification Service (email/push/telegram webhooks).
2.2.5. Admin Service (управление справочниками, мониторинг).
2.2.6. Analytics Service (события, воронки, KPI).

2.3. Интеграции
2.3.1. Поставщики авиабилетов (GDS/NDC/API агрегаторов).
2.3.2. Платежный провайдер (если будете продавать напрямую, иначе только редирект).
2.3.3. Email/SMS сервисы.
2.3.4. Гео/перевод/курсы валют API.

2.4. Нефункциональные требования
2.4.1. Время ответа поиска <= 2-4 сек (с учетом агрегации).
2.4.2. 99.9% uptime.
2.4.3. Горизонтальное масштабирование API.
2.4.4. Защита от DDoS и abuse.
